# 0114. The `?tune` panel and the balance check

**Status:** Implemented for review (2026-10-23). Steps 4 and 5 of [0093](0093-data-driven-content-and-authoring-tools.md), requested by Guillaume ("start … the two points we were keeping for later in data driven"). One decision and one pull request: the balance check lives inside the panel and shares its edit sets.

## Context

Since [0094](0094-tuning-moved-to-data.md), every tuning number is in `src/data/tuning/*.json` and the ship files of [0109](0109-one-file-per-ship.md), read live from one `TUNING` object, with a label, range, step, unit and help line for each in `src/data/tuning-meta.ts`. Changing a number still meant editing a file, reloading and, for the economy, running the balance tests. The two balance tests (0046 and 0083) each carried their own copy of the same 200-line simulation.

## Decision

1. **Opening.** Add `?tune` to the game's address (`…/fair-winds-trading/?tune`). The panel is its own lazy chunk (16 kB + 7 kB CSS, worker 98 kB): players never download it. In tune mode the game sails a **separate test voyage** (saves under `fwt.tune.play.`), so "sail this ship" and odd numbers never touch the real voyage; **New voyage** in the panel starts a fresh one and keeps the tuning.
2. **Panel.** Style D, touch-first: left of the game in landscape, a bottom sheet in portrait, **Hide** folds it to a "Tuning · N" pill. One tab per tuning file, built from `tuning-meta.ts` alone (a value added there shows up with no UI code): a slider and a number box per number (each element of a per-level table is its own row), a switch per on/off value, names and ids not shown. Collections (ships, goods, levels, weather kinds) get a picker. Changed rows are outlined in brass with a ↺ back to the shipped value; a tap on a name shows its help and the shipped value; the header counts the changes; **Reset all** puts everything back. Typed numbers are clamped to the meta range and snapped to its step, so an exported file always passes the tuning tests.
3. **Live.** Every edit changes `TUNING` in place (`setTuneValue`, arrays too, so the sim's aliases stay valid) and drops the weather caches (`clearWeatherCaches`, `clearDifficultyWeatherCache`), which are keyed by config object. Values read when a voyage starts (start gold) show on a new voyage. Edits are applied before the world is built on the next load.
4. **Ships tab.** The polar curve as a half rose, wind from the top, no-go zone shaded: drag a dot along its ray to change that angle's fraction (the angles stay); the shipped curve shows dashed once changed. Beside it: top speed in knots in the 14 kn reference breeze ([0075](0075-speed-in-knots.md); stock, full sails; the shipped value struck through when it differs), best angle and no-go. **Sail this ship** gives the test voyage that ship (stock) and switches to it at once.
5. **Edits are a flat record** of the values that differ from the shipped files, by dotted path (`{"ships.cutter.speedRatio": 0.69}`), in `src/data/tuningEdits.ts` (pure, tested). It is what the browser keeps (`fwt.tune.v1`, this browser only), what a share link carries and what the balance worker receives. Unknown or misshapen entries are skipped, so an old link survives a renamed value.
6. **Share.** A link `…/?tune#tune=FT1…` and its QR code, packed with zlib and URL-safe base64 like save transfer ([0066](0066-move-voyage-between-devices.md)). Opening it asks before it replaces that device's tuning.
7. **Export.** Each file holding a changed value, rebuilt whole from the live values: `src/data/tuning/<group>.json`, or `src/data/ships/<id>.json` with only its `sailing`, `unlock` and `tier` updated (model and hull untouched). `src/data/jsonFormat.ts` writes JSON exactly as Prettier formats these files (a test checks it byte for byte on every shipped tuning and ship file), so an uploaded file passes lint and its diff shows only the changed lines. Download one file, copy it, or download all as a zip with repository paths. How to get them into the game: [docs/tuning-panel/README.md](../tuning-panel/README.md).
8. **Balance check.** The simulation moved from the two tests into `src/sim/balance.ts` (`sailVoyage`, `economyRun`/`economyChecks`, `difficultyRun`/`difficultyChecks`); the targets moved to `src/data/balance-targets.json`. The tests now run it and assert every check, with the same results to the tenth of a minute as before. The panel runs it in a Web Worker (`src/tune/balance.worker.ts`) 0.7 s after the last edit, on the Windward Ring: the 40-minute Captain game (17 checks in all with the levels: first upgrade, cutter 9–16 min sharp, ≤ 32 relaxed, order share, routes, repairs) first, then each difficulty level over two hours. The panel shows "all N targets hold" or "N missed" and the cutter times; tapped, every check with its result and target. A new edit stops the run and starts again. It takes about two seconds on a computer.

## Consequences

- Guillaume can tune any number while sailing, on the tablet too, see whether the economy still holds, and hand the result over as files or a link.
- The balance targets are data: changing what "balanced" means is a reviewed edit of `balance-targets.json`, and the tests and the panel can never disagree.
- The "moved values equal the old constants" block in `tests/tuning.test.ts` stays until the first deliberate tuning change: the first exported file that lands removes it in the same pull request.
- The panel is English only, like the editors.
- Not covered: the map, town levels list, quests and music (their own files and editors), and values read once at load (ids, the list of levels). The balance check always uses the Windward Ring, the map its targets were set on.
